================================================================================
  ADMISSIONS SYSTEM API — Full Project Description
================================================================================

Overview
--------
This project is a REST API built with Python and FastAPI that manages a
multi-step admissions flow for an education platform. Users register, then
progress through an ordered sequence of steps (each containing one or more
tasks). External systems call a webhook endpoint to report task completion.
The API evaluates pass/fail conditions against the payload and determines
whether each user is ultimately accepted, rejected, or still in progress.

The key design principle is that the admissions flow is CONFIG-DRIVEN: steps
and tasks are defined in a JSON file (config/flow.json), not scattered across
business logic. Adding, removing, or reordering steps requires editing only
that file. Pass/fail evaluators are pure functions in isolated modules —
adding a new condition means adding one case to one function.


Tech Stack
----------
- Python 3.11+ with FastAPI (async web framework)
- Pydantic v2 for data validation and serialization
- In-memory storage (Python dicts — no database)
- uvicorn as the ASGI server
- pytest + httpx for testing

  DESIGN & ARCHITECTURE

High-Level Architecture
-----------------------
The system follows a LAYERED ARCHITECTURE with clear separation of concerns:

  ┌─────────────────────────────────────────────────────────┐
  │                     API Layer (Routes)                   │
  │   users.py    │    flow.py    │    tasks.py              │
  │   POST /users │    GET /flow  │    PUT /tasks/:id        │
  │   GET /progress                                          │
  │   GET /outcome                                           │
  └──────────────────────┬──────────────────────────────────┘
                         │ delegates to
  ┌──────────────────────▼──────────────────────────────────┐
  │                  Service Layer (Business Logic)          │
  │   user_service.py  │  task_service.py  │ flow_service.py │
  └──────────┬─────────┴────────┬──────────┴────────────────┘
             │                  │ calls
  ┌──────────▼──────────┐  ┌───▼──────────────────────┐
  │   Data Layer        │  │   Evaluators             │
  │   store.py          │  │   pass_condition.py      │
  │   (in-memory dicts) │  │   unlock_condition.py    │
  └─────────────────────┘  └──────────────────────────┘
             ▲
             │ populated at startup from
  ┌──────────┴──────────┐
  │   Config Layer      │
  │   flow.json         │
  └─────────────────────┘

Layer Responsibilities:

  1. CONFIG LAYER (config/flow.json)
     The static definition of the admissions pipeline. Defines what steps
     exist, what tasks each step contains, and what condition determines
     pass/fail for each task. This is the single source of truth — PMs
     can modify the flow without touching code.

  2. DATA LAYER (src/db/store.py)
     A single global in-memory store that holds both the loaded config
     (flow_steps, tasks) and runtime state (users, user_task_statuses).
     All other layers read from and write to this store.

  3. EVALUATOR LAYER (src/evaluators/)
     Pure functions with zero side effects. They take a condition key and
     a payload, and return a result. Completely decoupled from the rest
     of the system — they don't import the store, services, or routes.

  4. SERVICE LAYER (src/services/)
     Contains all business logic. Three services:
     - flow_service:  loads config, provides query helpers
     - user_service:  user registration and progress computation
     - task_service:  the core state machine for task completion

  5. API LAYER (src/routes/)
     Thin HTTP handlers that parse requests, call the service layer,
     and format responses. No business logic lives here.


Data Flow: Task Completion (Webhook)
------------------------------------
This is the most important flow in the system. Here is what happens when
an external system sends a PUT /users/{id}/tasks/{task_id} webhook:

  1. ROUTE receives the HTTP request
     └─ tasks.py extracts user_id, task_id from URL, payload from body

  2. SERVICE validates and processes
     └─ task_service.complete_task() runs the full state machine:

        a. LOOKUP user in store → 404 if not found
        b. LOOKUP task in store → 404 if not found
        c. CHECK user not rejected → 400 if already rejected
        d. CHECK UserTaskStatus exists → 400 if task not available
        e. CHECK idempotency → return early if already "passed"
        f. EVALUATE pass condition (delegated to evaluator layer)
        g. UPDATE UserTaskStatus with result + timestamp
        h. If FAILED → set User.status = "rejected"
        i. If PASSED → try unlocking conditional tasks
        j. If PASSED → check if ALL tasks now passed → "accepted"

  3. EVALUATOR determines pass/fail
     └─ pass_condition.evaluate() is a pure function:
        - "always" → "passed"
        - "score_gt_75" → check payload.score > 75
        - "decision_passed" → check payload.decision == "passed_interview"

  4. RESPONSE sent back
     └─ { "task_state": "passed" } or { "task_state": "failed" }


Data Flow: User Registration
-----------------------------
  1. POST /users with { "email": "..." }
  2. user_service.create_user():
     a. Check email uniqueness (scan store.users) → 409 if duplicate
     b. Generate UUID
     c. Create User(status="in_progress")
     d. For each non-conditional task in the flow:
        create UserTaskStatus(state="pending")
  3. Return { "user_id": "..." } with 201


Data Flow: Progress Query
--------------------------
  1. GET /users/{id}/progress
  2. user_service.get_user_progress():
     a. Walk flow steps in order (1 → 6)
     b. For each step, check all non-conditional tasks
     c. If ALL tasks in a step are "passed" → step is complete
     d. FIRST incomplete step = current_step
     e. Within that step, FIRST non-passed task = current_task
     f. Count completed steps for step_number
  3. Return { current_step, current_task, completed_steps,
              step_number, total_steps }


State Machine: User Status Transitions
---------------------------------------

                 ┌──────────────┐
                 │              │
  POST /users ──▶│ in_progress  │
                 │              │
                 └──────┬───────┘
                        │
            ┌───────────┴───────────┐
            │                       │
     any task fails          all tasks pass
            │                       │
            ▼                       ▼
   ┌────────────────┐    ┌─────────────────┐
   │   rejected     │    │    accepted      │
   │  (terminal)    │    │   (terminal)     │
   └────────────────┘    └─────────────────┘

  - "in_progress": Initial state. User is still completing tasks.
  - "rejected":    Terminal state. Any required task failed.
                   No further task completions are allowed (400).
  - "accepted":    Terminal state. All required tasks passed.


State Machine: Task Status Transitions
---------------------------------------

                 ┌──────────────┐
                 │              │
  user created ──▶│   pending   │
                 │              │
                 └──────┬───────┘
                        │
            ┌───────────┴───────────┐
            │                       │
     evaluator returns         evaluator returns
        "failed"                  "passed"
            │                       │
            ▼                       ▼
   ┌────────────────┐    ┌─────────────────┐
   │    failed      │    │     passed       │
   │  (terminal)    │    │   (terminal,     │
   └────────────────┘    │    idempotent)   │
                         └─────────────────┘


Entity Relationships
--------------------

  ┌─────────────┐ 1     * ┌──────────┐
  │  FlowStep   │────────▶│   Task   │
  │  (config)   │         │ (config) │
  └─────────────┘         └────┬─────┘
                               │
                         referenced by
                               │
  ┌─────────────┐ 1     * ┌───▼──────────────┐
  │    User     │────────▶│ UserTaskStatus    │
  │  (runtime)  │         │ (runtime)         │
  └─────────────┘         └───────────────────┘

  - FlowStep 1:* Task      — A step contains one or more tasks.
  - User 1:* UserTaskStatus — A user has one status per task.
  - Task referenced by UserTaskStatus via task_id.

  Config entities (FlowStep, Task) are loaded ONCE at startup and never
  change. Runtime entities (User, UserTaskStatus) are created and mutated
  as users register and complete tasks.


Design Patterns Used
--------------------

  1. EVALUATOR PATTERN
     Pass conditions and unlock conditions are implemented as pure functions
     with a match/case dispatch. This is essentially the Strategy pattern
     but simplified — instead of separate classes per strategy, it's a single
     function with branches. To add a new strategy, add one case.

  2. SINGLETON (Store)
     The in-memory store is a module-level instance. Every module imports
     the same object. This avoids dependency injection complexity while
     keeping all state in one place.

  3. SERVICE LAYER
     Business logic is concentrated in service modules, not in routes.
     Routes are thin wrappers that handle HTTP concerns (parsing, status
     codes, response formatting) and delegate everything else.

  4. CONFIG-DRIVEN BEHAVIOUR
     The flow is declarative data (JSON), not imperative code. The system
     interprets the config at runtime. This makes the flow modifiable
     without code changes and testable with different configs.

  5. DERIVED STATE
     User progress (current step, completed steps) is computed on the fly
     by walking the flow — it's not stored separately. This eliminates
     the risk of stale or inconsistent cached state.

  6. LIFESPAN PATTERN (FastAPI)
     The app uses FastAPI's async context manager lifespan to run startup
     logic (loading flow config) before the server accepts requests. This
     replaces the older @app.on_event("startup") pattern.


Why These Choices?
------------------

  Q: Why in-memory storage instead of a database?
  A: The exercise specifies in-memory storage. It keeps the project simple
     and focused on the business logic. The store can be replaced with a
     database later by changing only store.py and the service layer.

  Q: Why Pydantic models for everything?
  A: FastAPI integrates deeply with Pydantic. Request bodies are auto-parsed
     and validated. Response models are auto-serialized. OpenAPI docs are
     auto-generated. Using Pydantic throughout gives consistency.

  Q: Why separate evaluator modules?
  A: Pure functions are easy to test, easy to extend, and impossible to
     break other parts of the system with. They don't import the store
     or services — they only take inputs and return outputs.

  Q: Why tuple keys for UserTaskStatus?
  A: dict[(user_id, task_id)] gives O(1) lookups. The alternative would
     be nested dicts (users → tasks → status) which is harder to iterate
     and more error-prone. Tuples are hashable and immutable.

  Q: Why derive progress instead of storing it?
  A: Stored progress must be kept in sync on every state change. Derived
     progress is always correct by definition. The trade-off is
     computation cost per query, but with 6 steps and 8 tasks the
     overhead is negligible.

================================================================================
  FILE-BY-FILE DESCRIPTION
================================================================================


--- config/flow.json ---
PURPOSE: Static flow configuration that defines the admissions pipeline.
         This is the single source of truth for steps and tasks. PMs can
         modify the flow by editing this file — no code changes needed.

DETAILS: A JSON array of step objects. Each step has an id, name, order,
         and an array of tasks. Each task has an id, name, order, and a
         pass_condition key that maps to a case in the evaluator.
         Tasks can optionally have "conditional: true" and "unlock_when"
         for dynamic task unlocking (not currently used but supported).


--- src/app.py ---
PURPOSE: FastAPI application entry point. Creates the app, loads config
         on startup, and mounts all route modules.

FUNCTIONS:
  lifespan(app):
    - Async context manager used by FastAPI's lifespan feature.
    - On startup: calls load_flow_config() to parse flow.json and
      populate the in-memory store before any request is served.
    - On shutdown: yields (nothing to clean up for in-memory storage).

  app (module-level):
    - The FastAPI instance with title "Admissions System API".
    - Includes three routers: users_router, flow_router, tasks_router.

IMPLEMENTATION DETAIL: FastAPI's lifespan replaces the older @app.on_event
  decorators. It uses an async context manager — code before "yield" runs
  at startup, code after "yield" runs at shutdown.


--- src/models/schemas.py ---
PURPOSE: All Pydantic models for the project — data entities and API schemas.
         Pydantic provides automatic validation, serialization, and clear
         error messages when data doesn't match the expected shape.

MODELS (Config entities — loaded from flow.json):
  Task:
    - Represents a single task within a step.
    - Fields: id, step_id (default ""), name, order, pass_condition,
      conditional (default False), unlock_when (default None).
    - step_id is set at load time (not in the JSON) to link task → step.

  FlowStep:
    - Represents a step in the flow containing one or more tasks.
    - Fields: id, name, order, tasks (default []).

MODELS (Runtime entities — per-user mutable state):
  User:
    - Represents a registered user.
    - Fields: id, email, status (default "in_progress"), created_at.
    - Status transitions: in_progress → accepted (all tasks passed)
                          in_progress → rejected (any task failed)

  UserTaskStatus:
    - Tracks one user's state for one task.
    - Fields: user_id, task_id, state (default "pending"), completed_at.
    - State transitions: pending → passed, pending → failed.

MODELS (Request schemas):
  CreateUserRequest:
    - Body for POST /users. Contains: email (str).

MODELS (Response schemas):
  CreateUserResponse:  { user_id }
  TaskInfoResponse:    { id, name, order }         — lightweight task info
  StepInfoResponse:    { id, name, order, tasks }   — step with nested tasks
  FlowResponse:        { total_steps, steps }       — for GET /flow
  StepSummary:         { id, name, order }          — lightweight step info
  ProgressResponse:    { current_step, current_task, completed_steps,
                         step_number, total_steps }  — for GET /progress
  OutcomeResponse:     { status }                   — for GET /outcome
  TaskCompletionResponse: { task_state }            — for PUT /tasks

IMPLEMENTATION DETAIL: All models inherit from Pydantic's BaseModel. FastAPI
  uses these for automatic request body parsing, response serialization,
  and OpenAPI documentation generation. The "|" syntax (e.g. str | None)
  is Python 3.10+ union type syntax.


--- src/db/store.py ---
PURPOSE: In-memory data store. A single global instance holds all app state.
         No database needed — everything lives in Python dicts and lists.

CLASS Store:
  __init__(self):
    - users: dict[str, User]                          — keyed by user_id
    - user_task_statuses: dict[tuple[str,str], UTS]   — keyed by (user_id, task_id)
    - flow_steps: list[FlowStep]                      — ordered list of steps
    - tasks: dict[str, Task]                          — keyed by task_id

  store (module-level):
    - The singleton instance. Every module imports this same object.

IMPLEMENTATION DETAIL: Using a (user_id, task_id) tuple as the dict key
  gives O(1) lookups for any user-task combination, which is critical for
  the complete_task function that is called on every webhook. The store is
  a plain class (not a Pydantic model) since it's mutable runtime state.


--- src/services/flow_service.py ---
PURPOSE: Loads the flow configuration from JSON at startup and provides
         query helpers for retrieving steps and tasks in order.

FUNCTIONS:
  load_flow_config():
    - Reads config/flow.json, parses each step and its tasks into Pydantic
      models, and populates store.flow_steps and store.tasks.
    - Sets task.step_id to link each task back to its parent step.
    - Sorts flow_steps by order after loading.
    - Called once in the FastAPI lifespan hook.

  get_flow():
    - Returns all flow steps in order. Used by GET /flow endpoint.
    - Delegates to get_steps_in_order().

  get_steps_in_order():
    - Returns store.flow_steps sorted by the order field.

  get_tasks_for_step(step_id):
    - Finds the step with the given ID and returns its tasks sorted by order.
    - Returns [] if the step is not found.

IMPLEMENTATION DETAIL: CONFIG_PATH is computed relative to the file's location
  using Path(__file__).resolve() so it works regardless of the working directory.
  Tasks are stored in two places: inside their parent FlowStep.tasks list AND
  in the flat store.tasks dict — the former preserves hierarchy, the latter
  enables O(1) lookup by task_id.


--- src/services/user_service.py ---
PURPOSE: All user-scoped business logic — registration, progress computation,
         and outcome retrieval.

FUNCTIONS:
  create_user(email):
    - Checks email uniqueness (raises 409 Conflict if duplicate).
    - Generates a UUID, creates a User with status "in_progress".
    - Creates a UserTaskStatus (state="pending") for every non-conditional
      task in the flow. This seeds the user's task tracker.
    - Returns the user_id string.

  get_user(user_id):
    - Looks up a user in the store by ID.
    - Raises HTTPException 404 if not found.

  get_user_progress(user_id):
    - Walks all steps in order. For each step, checks whether all
      non-conditional tasks are "passed".
    - The first step that is NOT fully passed becomes current_step.
    - Within that step, the first non-passed task becomes current_task.
    - Builds a list of completed_steps (step IDs fully passed).
    - Computes step_number (1-indexed) and total_steps.
    - If all steps are done: current_step=None, current_task=None.

  get_user_outcome(user_id):
    - Returns the User.status field directly ("in_progress", "accepted",
      or "rejected"). The status is eagerly updated by complete_task.

IMPLEMENTATION DETAIL: Progress is DERIVED, not stored. It walks the flow
  config each time, checking task statuses. This means it's always accurate
  and doesn't need to be kept in sync. Conditional tasks are excluded from
  total_steps counting.


--- src/services/task_service.py ---
PURPOSE: The core state machine driver. Processes task completion webhooks,
         evaluates pass/fail, manages user status transitions, and handles
         conditional task unlocking.

FUNCTIONS:
  complete_task(user_id, task_id, payload):
    The main entry point for task completion. Steps:
    1. Validate user exists (404 if not).
    2. Validate task exists in config (404 if not).
    3. If user is already rejected, return 400.
    4. Check that user has a UserTaskStatus for this task (400 if not).
    5. IDEMPOTENCY: if task already "passed", return early.
    6. Evaluate the pass condition against the payload.
    7. Update UserTaskStatus with result + timestamp.
    8. If FAILED: set User.status = "rejected", return.
    9. If PASSED: try to unlock any conditional tasks.
    10. Check if ALL required tasks are now passed → set "accepted".
    11. Return the task state ("passed" or "failed").

  _try_unlock_conditional_tasks(user_id, payload):
    - Scans every conditional task in the flow.
    - Skips tasks already unlocked (already have a UserTaskStatus).
    - Evaluates should_unlock() for each — if True, creates a new
      UserTaskStatus (state="pending") for that task.
    - Catches ValueError from unknown unlock conditions (future-proofing).

  _all_required_tasks_passed(user_id):
    - Walks all tasks in the flow.
    - For conditional tasks: if the user doesn't have a UserTaskStatus
      for it (never unlocked), skip it — it's not required.
    - For all other tasks (and unlocked conditional tasks): checks that
      state == "passed".
    - Returns True only if every applicable task is passed.

IMPLEMENTATION DETAIL: The webhook is IDEMPOTENT — if a task is already
  "passed", the function returns immediately without re-evaluating.
  This handles duplicate webhook deliveries gracefully. Out-of-order
  webhooks are also handled: since all non-conditional tasks get
  UserTaskStatus rows at user creation, any task can be completed
  regardless of step order.


--- src/evaluators/pass_condition.py ---
PURPOSE: Pure function that determines pass/fail based on the task's
         configured condition and the webhook payload.

FUNCTIONS:
  evaluate(pass_condition, payload):
    - Uses Python's match/case (structural pattern matching) to dispatch:
      "always"          → always returns "passed"
      "score_gt_75"     → "passed" if payload["score"] > 75, else "failed"
      "decision_passed" → "passed" if payload["decision"] == "passed_interview"
      default           → raises ValueError

IMPLEMENTATION DETAIL: This is the EVALUATOR PATTERN. To add a new
  pass condition (e.g. "score_gt_60"), just add one case here. Nothing
  else in the system needs to change. The function is completely pure —
  no side effects, no state, easy to test. The match/case syntax requires
  Python 3.10+.


--- src/evaluators/unlock_condition.py ---
PURPOSE: Pure function that determines whether a conditional task should
         be unlocked for a user. Currently a generic skeleton with no
         specific conditions implemented.

FUNCTIONS:
  should_unlock(unlock_when, payload):
    - Takes the unlock_when key and the payload.
    - Currently only has the default branch which raises ValueError.
    - To add a condition (e.g. "score_between_60_75"), add a case.

IMPLEMENTATION DETAIL: This module is intentionally empty of specific
  logic — it's a placeholder for future extensibility. When a conditional
  task is added to flow.json with an unlock_when key, a corresponding
  case should be added here.


--- src/routes/users.py ---
PURPOSE: Route handlers for user-related endpoints.

ENDPOINTS:
  POST /users (post_user):
    - Accepts CreateUserRequest (email), calls create_user().
    - Returns CreateUserResponse (user_id) with status 201.

  GET /users/{user_id}/progress (get_progress):
    - Calls get_user_progress() to compute flow position.
    - Converts internal FlowStep/Task objects to response schemas
      (StepSummary, TaskInfoResponse).
    - Returns ProgressResponse.

  GET /users/{user_id}/outcome (get_outcome):
    - Calls get_user_outcome() which returns the status string.
    - Returns OutcomeResponse.


--- src/routes/flow.py ---
PURPOSE: Route handler for the flow definition endpoint.

ENDPOINTS:
  GET /flow (get_flow_definition):
    - Calls get_flow() to get all steps.
    - Filters out conditional tasks from each step's task list.
    - Returns FlowResponse with total_steps and nested steps/tasks.


--- src/routes/tasks.py ---
PURPOSE: Route handler for the task completion webhook.

ENDPOINTS:
  PUT /users/{user_id}/tasks/{task_id} (put_complete_task):
    - Reads the raw JSON body as the task payload.
    - Calls complete_task() which runs the full state machine.
    - Returns TaskCompletionResponse with the resulting task_state.

IMPLEMENTATION DETAIL: This endpoint uses Request.json() to accept
  any arbitrary JSON body (rather than a fixed Pydantic model), because
  different tasks have different payload structures. The payload is
  passed directly to the evaluator.


================================================================================
  EDGE CASES HANDLED
================================================================================

  1. Duplicate webhook:     If a task is already "passed", returns success
                            without re-evaluating (idempotent).
  2. Unknown task_id:       Returns 404 "Task not found".
  3. Out-of-order webhooks: Accepted — since all non-conditional tasks get
                            UserTaskStatus rows at creation, any task can
                            be completed regardless of step order.
  4. User not found:        Returns 404 on all user-scoped endpoints.
  5. Task after rejection:  Returns 400 "User has been rejected".
  6. Duplicate email:       Returns 409 "Email already exists".

================================================================================
  KEY IMPLEMENTATION DETAILS
================================================================================

1. CONFIG-DRIVEN FLOW
   Steps and tasks are defined in config/flow.json, not in code. The flow
   service loads this once at startup. To modify the admissions pipeline,
   edit the JSON file — no business logic changes required.

2. EVALUATOR PATTERN
   Pass conditions and unlock conditions are pure functions in isolated
   modules. They take a condition key + payload and return a result.
   Adding a new condition = adding one "case" to one function. This keeps
   the system extensible without modifying routing or service logic.

3. SEPARATION OF CONFIG AND STATE
   FlowStep and Task are config (shared, immutable after load).
   UserTaskStatus is the only per-user mutable state. Step completion
   and user outcome are DERIVED from task states — not stored separately.

4. IN-MEMORY STORE WITH TUPLE KEYS
   UserTaskStatus is keyed by (user_id, task_id) tuples for O(1) lookups.
   This is critical for performance in complete_task which is called on
   every webhook.

5. IDEMPOTENT WEBHOOKS
   If a task is already "passed", complete_task returns immediately without
   re-evaluating. This safely handles duplicate webhook deliveries.

6. EAGER STATUS UPDATES
   User.status is updated immediately when a task is completed:
   - Any task fails → status = "rejected"
   - All tasks pass → status = "accepted"
   This means the GET /outcome endpoint is a simple field read.

7. OUT-OF-ORDER RESILIENCE
   All non-conditional tasks get UserTaskStatus rows when a user is created.
   This means any task can be completed regardless of step order — the API
   is resilient to out-of-order webhook deliveries.

8. CONDITIONAL TASKS (EXTENSIBLE)
   The framework supports conditional tasks (hidden by default, unlocked
   dynamically). The unlock evaluator is a generic skeleton ready for
   future conditions. To add one: add a case to should_unlock() and a
   conditional task entry in flow.json.

9. TEST ISOLATION
   The autouse reset_store fixture clears all store state before every test,
   preventing state leakage. Tests that need the flow config use the
   loaded_flow fixture which re-loads flow.json into the clean store.

10. HOW TO RUN
    pip install -r requirements.txt
    uvicorn src.app:app --reload        # Start the server
    pytest -v                           # Run all tests
